# 4·5단계 실행 계획과 LLM 전략

## 목적

3단계(문서 작성)가 끝난 뒤 남는 두 단계, 즉 4단계 교차 일관성(cross-document consistency)과 5단계 마감(README·CLAUDE.md·최종 지도)의 **할 일 목록, 실행 순서, 모델 배분, 예상 비용**을 확정한다. 3단계까지 6.68B 토큰(비용의 85~89%가 캐시 쓰기)이 들었으므로, 이 계획의 제1 원칙은 **에이전트 수를 줄이고 기계 처리를 앞세우는 것**이다.

## 범위

- 포함: 3단계 결과 JSON(`tools/phase3/results/*.json`)에 누적된 미해결 이슈 354건(바이블 관련 138건), 계약 감사 정본 결정 47건의 하류 전파, 완전성 비평 결과, 규약 위반(분량·상태·ID 접두·링크), 경량 모드 수정분의 표본 검증, 마감 산출물.
- 제외: 새 설계 결정(ADR-0039 이후 제안은 목록화만), 코드 구현, 영어 전문 번역(README의 영어 요약만).

## 1. 원칙

1. **기계가 먼저, LLM은 판단에만.** 링크·철자·frontmatter·분량·ID 접두 같은 결정적(deterministic) 검사와 치환은 Node 스크립트로 처리한다. LLM 에이전트는 "바이블을 고칠지 말지"와 "문장을 어떻게 고칠지"에만 쓴다.
2. **앵커 읽기 비용을 나눠 낸다.** 에이전트 1개가 문서 3~6개를 묶어 처리한다(문서당 1 에이전트 금지). 앵커(브리프·바이블 절·계약 개요) 읽기 약 7~10M 토큰이 에이전트 단위로 발생하기 때문이다.
3. **모델은 판단 난도에 맞춘다.** 바이블 개정 판정은 Opus 5(effort high), 지시가 명확한 편집·검증은 Sonnet 5, 결정적 작업은 스크립트.
4. **정본 방향은 바이블 → 문서.** 문서의 개정 요청은 먼저 바이블에서 채택/기각을 판정하고, 채택된 것만 전파한다. 문서가 바이블을 앞질러 바뀌는 일은 없다.
5. **모든 단계 뒤에 기계 검증.** `tools/validate-contracts.mjs`(계약·스키마)와 신설 `tools/audit-docs.mjs`(전 문서)가 0 오류여야 다음 단계로 간다.

## 2. 4단계 할 일

### 2.1 기계 처리(LLM 없음) — `tools/audit-docs.mjs` 신설

| 검사·치환 | 내용 | 산출 |
|-----------|------|------|
| A1 링크 | 모든 `docs/**/*.md`의 상대 링크가 실제 파일을 가리키는지. 브리프 §8 문서 맵에 없는 경로 링크 검출 | 깨진 링크 목록, 자동 수정(경로 오탈자·이동된 문서) |
| A2 frontmatter | 필수 필드(title, status, owner, version, last_updated, depends_on; 계약은 schema_version; ADR은 date·deciders·priority·related), status 허용값, 날짜 형식 | 누락 자동 삽입(version 0.1.0 등), 위반 목록 |

| A4 ID 접두 | 비전 문제 `PB-xx`, 목표 `G-xx`, 원칙 `DP-xx`, 용어집 이슈 `G-xx`, 링크 키 `[P-xx]`, KPI·SC·DF·UC·US·FR·NFR 사용 지도 | 충돌 지도. 결정(§2.3 D4-1) 후 정규식 치환 |

| A7 인용 무결성 | ADR 번호·D-xx·O-xx·FR/NFR/UC/US ID 인용이 정의 문서에 존재하는지 | 미정의 인용 목록 |
| A8 "확인 필요" | `확인 필요(as of 2026-09)` 표기 집계(문서별) | 후속 검증 백로그(4단계 범위 밖, 목록만) |
| A9 스키마 인벤토리 | `schemas/*.json` ↔ 바이블 §5.1 표 대조(현재 `schema-diff-report.schema.json` 미등재) | 불일치 목록 |

### 2.2 LLM 판정 — 바이블 개정 트리아지(Opus 5)

입력: 결과 JSON의 미해결 이슈 중 바이블 관련 138건(아키텍처 23, 계약 53, 파이프라인 62) + 마무리 실행(API·평가·운영·개발·로드맵)과 완전성 비평이 추가하는 건 + 계약 감사 정본 결정 47건 + A9.

| 단계 | 에이전트 | 내용 | 산출 |
|------|---------:|------|------|
| T1 분류 | Opus 1 (주제별로 나누면 최대 3) | 각 요청을 채택(patch/minor/major)·기각·보류로 판정, 근거와 영향 문서 목록 작성. 바이블 §1.2 절차 준수. 중복 요청 병합 | `12-appendix/03-bible-amendment-triage.md` (표: 요청 | 출처 문서 | 판정 | 바이블 절 | 영향 문서) |
| T2 개정 | Opus 1 | 채택분을 바이블에 반영(버전 1.3.0 또는 1.2.x — major 변경이 없으면 minor), 브리프 §4·§8 동기화, 계약 `schema_version` 영향 판단 | 개정된 바이블·브리프, 전파 지시서(문서별 변경 항목) |
| T3 스키마 | 스크립트 + Sonnet 1 | 바이블 열거·필드 변경을 `schemas/*.json`과 03-contracts 문서 블록에 반영 | 검증기 0 오류 |

### 2.3 결정이 필요한 항목(트리아지 전에 확정)

| ID | 결정 | 제안 |
|----|------|------|
| D4-1 | ID 접두 충돌 해소 | 비전 목표 `G-xx` 유지(대표 문서), 용어집 미해결 이슈 `G-xx` → `GL-xx`, 용어집 링크 키 `[P-xx]` → `[PL-xx]`, 원칙 `DP-xx`·문제 `PB-xx` 유지 |
| D4-2 | 900행 초과 처리 | 계약 문서는 스키마 전문 포함이라 예외(브리프 §9.11). 비계약 9건은 절 이관(예: 02-architecture/02 설정 모델 → 09-operations/02, 06 사가 상세 → 04-pipelines/19, 04-pipelines/01 CLI·테스트 유틸 → 10-development/04)으로 900행 이내 |
| D4-3 | 바이블 버전 | 채택 개정에 필드 제거·의미 변경이 없으면 1.3.0(minor), 있으면 2.0.0과 영향 문서 일괄 개정. 목표는 1.3.0 |
| D4-4 | 경량 모드 검증 표본 | 경량 리뷰로 수정된 약 69건(문서 31 + ADR 38) 중 20%(14건: 계약 의존도가 높은 파이프라인·API 우선)를 Sonnet 리뷰어가 검증, 심각 이슈 발견율 10% 초과 시 표본 확대 |

### 2.4 LLM 전파·편집(Sonnet 5)

| 단계 | 에이전트 | 묶음 단위 | 내용 |
|------|---------:|-----------|------|

## 4. 모델 배분과 예상 비용

| 구분 | 모델 | 에이전트 | 에이전트당 토큰(추정) | 소계 토큰 | 소계 비용(추정) |
|------|------|--------:|----------------------:|----------:|----------------:|
| 기계 감사·치환(A1~A9, 상태·frontmatter·LICENSE·스키마 인덱스) | 없음 | 0 | 0 | 0 | 0 |
| 바이블 트리아지·개정(T1~T2) | Opus 5, effort high | 2~4 | 10~15M | 30~60M | $60~120 |
| 스키마 동기화(T3) | Sonnet 5 | 1 | 8M | 8M | $10 |
| 전파·분량·표본 검증·잔여(P1~P4) | Sonnet 5 | 24~27 | 7~9M | 170~240M | $240~330 |
| 마감(README·CLAUDE.md) | Sonnet 5 | 2 | 6M | 12M | $15 |
| **합계** | | **29~34** | | **0.22~0.32B** | **$325~475** |

비교: 3단계 방식(Fable 5.1, 문서당 에이전트 4~5개)으로 같은 범위를 처리하면 약 150 에이전트, 1.0~1.5B 토큰, $6,000~9,000 규모다. 단가는 공시 가격(Opus $5/$25, Sonnet $2/$10)과 캐시 배수 가정(쓰기 2×, 읽기 0.1×)에 근거한 추정이며, 계약 단가로 재계산해야 한다.

오케스트레이터(메인 세션) 비용은 별도다. 메인 세션 모델을 Opus 5로 낮추면 4·5단계 지시·검토 턴의 비용도 절반이 된다. 스크립트 작성·결과 판독이 주 업무이므로 품질 손실은 작다.
